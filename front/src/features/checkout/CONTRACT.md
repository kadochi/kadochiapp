# Checkout contract

`getCheckoutState` and `submitCheckout` use `/api/checkout` and Woo Store API only, always `no-store`. Checkout is available in every environment when its required WooCommerce gateway and shipping configuration are present. Submissions are never retried and include a caller-generated operation ID; the selected gateway must support idempotency.

Checkout BFF handlers require a valid HttpOnly auth token and forward it with the HttpOnly Cart Token. The current cart is therefore converted into an order for the authenticated Woo customer. `CheckoutState` is `{ cart, customer, deliverySlots, packagingOptions, paymentMethod }`; its single payment method is `KADOCHI_PAYMENT_METHOD_ID` (default `WC_ZPal`, supplied by the provisioned official ZarinPal plugin) and checkout fails closed when that ID is absent from `cart.payment_methods`. The checkout saves its Tehran delivery address to the Woo cart before the delivery step, then displays Woo's resulting shipping and tax totals before payment. The payment step applies and removes Woo coupons via same-origin cart BFF routes, so totals and the cart token remain server-controlled.

Browser checkout input contains sender/recipient/address, an optional map-selected delivery location, delivery, packaging, postcard, and operation data only. The BFF derives the sender's phone and email and fixed `IR`/`تهران` values, persists validated additional checkout fields to the Woo draft, repeats them on POST for WooCommerce 10.8+ compatibility, then processes payment. A retryable failure after payment submission is reconciled via the owner-scoped operation summary and never triggers an automatic retry. Woo's structured HTTP 400 gateway-failure result is parsed as a checkout result; unrelated 400 responses still fail closed.

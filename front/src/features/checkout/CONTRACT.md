# Checkout contract

`getCheckoutState` and `submitCheckout` use `/api/checkout` and Woo Store API only, always `no-store`. Checkout is available in every environment when its required WooCommerce gateway and shipping configuration are present. Submissions are never retried and include a caller-generated operation ID; the selected gateway must support idempotency.

Checkout BFF handlers require a valid HttpOnly auth token and forward it with the HttpOnly Cart Token. The current cart is therefore converted into an order for the authenticated Woo customer. `CheckoutState` is `{ cart, customer, deliverySlots, packagingOptions, postcardDesigns, paymentMethods, savedAddresses }`. `paymentMethods` is the ordered allow-list `KADOCHI_PAYMENT_METHOD_IDS` (falling back to `KADOCHI_PAYMENT_METHOD_ID`, default `WC_ZPal`) intersected with `cart.payment_methods`; checkout fails closed when nothing remains. Snapp! Pay (`kadochi_snapppay`, `provider: "snapppay"`) is included only when WordPress reports it eligible for the current Rial total, and its `title`/`description` are Snapp's text, rendered verbatim. `GET /api/checkout/payment-methods` re-evaluates the list after a coupon changes the total. The checkout saves its Tehran delivery address to the Woo cart before the delivery step, then displays Woo's resulting shipping and tax totals before payment. The payment step applies and removes Woo coupons via same-origin cart BFF routes, so totals and the cart token remain server-controlled.

Browser checkout input contains sender/recipient/address, an optional map-selected delivery location, delivery, packaging, postcard message, one postcard design ID, an optional `paymentMethodId` (default: the first offered method), and operation data only. The BFF rejects a method that is not currently offered and re-checks Snapp! Pay eligibility immediately before the order POST; a stale choice returns a `validation` error with `fieldErrors.paymentMethodId`. A Snapp! Pay redirect must be an HTTPS URL on its API host or `SNAPPPAY_PAYMENT_HOSTS`. The BFF derives the sender's phone and email and fixed `IR`/`تهران` values, persists validated additional checkout fields to the Woo draft, repeats them on POST for WooCommerce 10.8+ compatibility, then processes payment. WordPress validates the selected published design and snapshots its title onto the order for fulfillment. A retryable failure after payment submission is reconciled via the owner-scoped operation summary and never triggers an automatic retry. Woo's structured HTTP 400 gateway-failure result is parsed as a checkout result; unrelated 400 responses still fail closed.
